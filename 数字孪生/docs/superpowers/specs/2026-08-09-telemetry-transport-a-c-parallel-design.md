# V1-B3 遥测传输 A/C 并行设计

状态：设计草案，等待用户审阅。

## 1. 背景与问题边界

本设计处理 V1-B3 同步采集中的遥测传输背压和证据边界问题，不修改 PID、循线、AprilTag 检测或 MPU6050 控制逻辑。

当前真实运行 `c260809102554685` 已记录：

- `telemetry_generated=223`，`telemetry_overwritten=18`；
- `CIPSEND` 最大事务时长约 364 ms；
- UART TX/RX 溢出和 ORE 均为 0，主循环最大间隔约 7 ms；
- 遥测 tick 存在约 257、226、193 ms 的间隔缺口；
- 主机原始遥测记录为 229 条，与健康统计的 223 条生成帧不一致；
- 当前同步门仍要求覆盖率 `>=95%`，时间差 p95 `<=33.3 ms`。

已确认的实现事实：

1. 固件使用 31 字节遥测帧、8 帧 latest-wins 缓冲和最多 248 字节 CIPSEND payload。
2. `ESP_TrySendTelemetry()` 在启动 CIPSEND 时立即消费遥测批次，没有等待 `SEND OK`。
3. 主机读取线程在 START 前启动，并在 STOP 清理完成前继续解析，因此边界外帧可能进入同一遥测列表。
4. 主机在解析回调中为每个帧单独调用 PC 时钟；同一个 socket `recv()` 批次中的多个帧没有共享真实到达时间。

具体的平均发送能力、ESP AT 固件对透明传输的支持情况和当前服务端/客户端拓扑仍需验证，不能仅凭最大事务时长推断透明模式一定有效。

## 2. 目标与非目标

### 目标

- 在保持现有 ESP-01S、30 ms 遥测生成周期、AA55 帧格式、P/R/A/S 协议、心跳、STOP 和安全租约的前提下，分别实现两种可回滚的传输后端。
- A 后端修复当前 CIPSEND 路径的队列所有权、发送失败保留和主机采集边界。
- C 后端验证 ESP-01S 透明 TCP 传输是否能去除 CIPSEND 事务造成的发送长尾。
- 两个后端使用同一套上层帧解析、实验存储、同步指标和验收门，保证 A/B 对比可解释。

### 非目标

- 不同时启用两个 TCP 客户端或两个发送器。
- 不新建第二套心跳、控制协议、ACK 注册表、AA55 解析器或 session 存储。
- 不在本阶段修改相机分辨率、AprilTag 阈值、PID、循线算法或 PCB。
- 不把透明传输的网络连续性假设为已证实。

## 3. 统一架构

上层只依赖一个传输能力边界：

```text
控制协议 / AA55 帧 / 心跳 / 实验采集器
                    |
          单一 Transport Adapter Contract
              /                     \
       A: AT+CIPSEND          C: Transparent TCP
       (默认后端)              (实验后端)
              \                     /
                 ESP-01S + TCP
```

A 和 C 是互斥的构建配置或固件变体。运行时只能选择一个后端；不允许自动在两种模式之间切换，更不允许在运动期间尝试 `+++` 或重新配置 ESP。

统一契约至少包含：初始化、逐字节接收、连接代次/断线状态、控制帧接收、ACK/STATUS 排队、遥测发送、发送结果和安全停机通知。现有 `esp_runtime_transport`、`twin_control_protocol`、`tx_frame_queue`、`esp_tx_coordinator` 和 AA55 parser 能复用的部分必须继续复用。

## 4. A 后端设计：保留 AT+CIPSEND

### 4.1 主机证据边界

- socket reader 可以在 START 前启动以避免丢失握手状态，但所有帧必须带有采集阶段标记。
- 只有匹配本次 `run_id` 的 RUNNING 状态之后、正式采集截止时间之前的遥测和位姿进入 B3 同步数据集。
- START 前、首次 RUNNING 前、正式截止后和 STOP 清理期间的数据单独写入 boundary evidence，不参与同步门。
- 每次底层 `recv()` 记录一次 `arrival_pc_ns`；同一批解析出的帧共享该到达时间，同时保留 `decode_pc_ns` 作为诊断字段。
- 同步报告必须同时报告窗口内遥测数、窗口外遥测数、健康统计生成数和帧 tick 范围，不能把不同口径合并成一个 `n_telemetry`。

### 4.2 固件队列所有权

- CIPSEND 启动时复制当前批次到在途事务，但不立即从逻辑队列提交消费。
- 只有收到 `SEND OK`，该批次才从逻辑队列移除。
- `ERROR`、`busy`、`CLOSED` 或超时必须按现有连接代次规则保留或丢弃，并在健康统计中明确分类。
- 新生成的遥测进入有界 FIFO；不能因为普通遥测追赶而静默覆盖同步关键帧。
- 队列容量、批次大小和是否增加 payload 上限必须由真实日志重放决定，不预先硬编码 16/32 帧。
- ACK、STATUS、Health 继续保持现有优先级和安全语义，不得用遥测队列吞掉关键控制帧。

### 4.3 A 的验证

离线验证必须覆盖：

- CIPSEND 成功、失败、超时和断线时的队列提交语义；
- 在途批次与待发队列不会重复、乱序或丢失提交状态；
- 真实日志回放下的队列峰值、批次大小、预计服务率和溢出风险；
- START/STOP、ACK/STATUS、心跳和连接代次回归。

## 5. C 后端设计：透明 TCP 实验路径

### 5.1 工作方式

透明模式只在连接建立阶段使用 AT 配置；进入透明发送状态后，STM32 UART 上的应用数据直接作为 TCP 数据流发送。上层仍使用现有 AA55 帧和 P/R/A/S 内容，ESP 不参与应用层解析。

具体初始化命令不能先写死，必须先读取并记录 ESP AT 固件版本、`CIPMODE`、单连接/多连接能力以及当前 TCP server/client 拓扑的兼容性。

### 5.2 连接和安全状态机

C 后端必须明确以下状态：命令模式、配置中、TCP 已连接、透明数据中、断线恢复、失败安全停机。透明模式下若无法可靠判断连接已经断开，必须由 MCU 心跳租约和本地超时触发电机停止，而不能继续运动。

`+++` 只允许在电机已停止、发送流已静默且满足 guard time 的恢复流程中使用；不能把它作为运行期间的普通控制手段。

### 5.3 C 的复用边界

复用：

- `twin_control_protocol`；
- AA55 帧格式和 PC `MixedStreamParser`；
- heartbeat、START/STOP、session/run_id 和证据存储；
- 连接断线后的安全策略和回滚语义。

新增或替换：

- ESP 透明模式生命周期适配器；
- 透明模式的连接边界和恢复检测；
- C 后端专用的构建配置、能力声明和诊断字段。

## 6. 两条线路的执行顺序

1. 先完成 A 的主机证据边界和固件队列设计，并在离线测试中确定最小必要改动。
2. 同时可以编写 C 的接口、状态机和 Host C 测试，但不连接硬件、不进入透明模式。
3. A 和 C 分别编译为互斥固件变体，保留当前 CIPSEND 版本作为回滚基线。
4. A 先进行硬件验证；若 A 达到同步门，C 仍作为对照实验，不得宣称更优。
5. 若 A 在证据口径正确且队列无覆盖的前提下仍受 CIPSEND 长尾限制，再授权 C 进行 ESP 能力检查和短时硬件实验。
6. C 的实验必须使用与 A 相同的采集时长、相机配置、run 结构和验收门。

## 7. 共同验收条件

每个后端都必须独立满足：

- 固件可在 Keil 中无错误、无警告构建；
- Host C/Python 回归通过；
- 没有第二套 TCP、心跳、协议或解析器；
- UART 无 RX/TX overflow、无 ORE；
- START/RUNNING、心跳、STOP/STOPPED、断线安全停机均有证据；
- 正式窗口内同步遥测无静默覆盖；
- B3 同步覆盖率 `>=95%`，时间差 p95 `<=33.3 ms`；
- 失败时结论为 `FAIL` 或 `INSUFFICIENT EVIDENCE`，不得由模型补齐缺失帧。

C 只有在相同条件下相对 A 同时表现出更低的发送长尾或更高的同步质量，才被判定为有效改进；仅仅“能连接”或“能收到数据”不算成功。

## 8. 当前未决问题

- 当前 ESP-01S AT 固件版本和透明模式能力尚未在本轮确认。
- 当前 server/client 拓扑是否兼容透明模式尚未确认。
- 当前 CIPSEND 事务时长的完整分布尚未保存，只有健康统计的聚合证据。
- `telemetry_generated` 与主机 raw telemetry 的窗口外差异需要先修正采集口径。
