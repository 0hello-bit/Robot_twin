# Task 4B-D / 4B-1 / 4B-2 返工与重新验收设计

## 目标

只修复独立审核发现的三个证据缺口，不重做已经通过的 4B-3，不扩大到 MCU、ESP、固件、烧录或车辆运动。

## 已确认问题

1. 4B-D 的交接文档仍明确记录人工验收 gate 为 `NOT MET`，后续任务却已经继续，计划状态与执行事实不一致。
2. 4B-1 的 600 秒统计满足帧率、丢帧率和时间戳门槛，但保存的起始证据是 DroidCam 启动画面，不能证明计时区间从第一帧起就是有效赛道画面。
3. 4B-2 的相机标定数值通过，但 `centerline_final.png` 中的红线包含贴边、分叉或尖刺，不能直接证明输出是一条可用于横向误差计算的赛道中心线。

## 返工设计

### 4B-D

逐条复核原 4B-D 清单与当前 spec/plan。不得直接把 `NOT MET` 替换成 `PASS`。新报告必须列出每个条目、对应文件和行号、结论与证据；全部满足后才能给出独立复核候选状态，否则保持 FAIL 并列出剩余差异。

### 4B-1

保留原有 Gate 0 指标：计时区间连续 600 秒、有效帧率至少 20 fps、drop 不超过 5%、时间戳严格单调。增加证据完整性要求：

- 明确记录 OpenCV 实际协商分辨率，目标为 1280×720；若设备拒绝该分辨率，报告必须 FAIL，不能把请求值当成实际值。
- 正式计时前设置 warm-up 阶段；DroidCam 启动页、全黑帧、冻结帧或读取失败不得进入正式 600 秒区间。
- 计时区间保存首帧、中帧、末帧和缩略图 montage；三者必须是赛道画面。
- 统计连续重复帧、近黑帧和低信息帧。自动检查只负责排除明显无效输入，赛道覆盖仍由独立审核者查看图片确认。
- 原始报告必须包含开始/结束单调时钟、总尝试数、有效帧数、失败数、fps、drop、重复帧率、无效内容帧数和实际分辨率。

### 4B-2

保留已经通过的内参和 homography，除非诊断证明它们是中心线错误的根因。先用现有赛道图片复现当前异常，再以测试驱动修复赛道地图提取：

- 最终中心线必须位于黑线内部且接近黑线中轴，不得只是轮廓边缘。
- 输出必须具有明确拓扑。若赛道本身有分支，必须输出分支图或基于已有文档确定唯一固定路线；不得把多个分支静默拼成一条跳跃点列。若无法从现有资料确定固定路线，必须报告 `NEEDS_USER_ROUTE_CHOICE`，不能臆测。
- 对中心线做连续性、相邻点最大跳变、端点/分支点数量、短毛刺长度和到边界距离检查。
- 新增能杀死“轮廓被当成中心线”“点列跨越空白区域”“短毛刺残留”的自动测试，并保存 RED→GREEN 证据。
- 生成最终 overlay：原图、黑线 mask、中心线和拓扑节点分色显示；独立审核者能够直接判断中心线是否位于黑线中间。
- 相机标定自动门仍为重投影误差 p95 不超过 `max(2 px, 真实黑线宽度像素的 5%)`。

## 安全与范围

- 允许：读取/修改 4B-D 文档、`v1_twin_camera.py`、`v1_twin_track_map.py` 及其直接测试；使用 DroidCam 读取画面；在新的 `.embeddedskills/build/v1_task4b_reacceptance/` 中写证据。
- 禁止：连接或复位 MCU、烧录、擦除 Flash、控制电机、使用 ESP/TCP、修改固件/Keil 工程、重做 4B-3 及后续模型、`git init`。
- 不允许删除或覆盖旧验收目录；新证据必须独立保存。

## 完成定义

只有以下条件同时成立才允许报告“返工完成”：4B-D 逐项复核无未解决项；4B-1 新鲜 600 秒硬件运行满足全部门槛且首/中/末图像均有效；4B-2 自动拓扑检查通过且最终叠加图经独立人工确认。代理完成只代表“待独立验收”，最终 PASS 由 Codex 独立复验后给出。
